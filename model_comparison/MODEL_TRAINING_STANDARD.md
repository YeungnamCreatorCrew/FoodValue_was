# 가격 예측 모델 비교 실험 기준서 v1

이 문서는 [공통 규약](MODEL_TRAINING_TEAM_CONVENTIONS.md)의 "시작 전 팀 확정표"에서 미정이던 항목을 **구체적인 값으로 정한 실행 기준**이다.
규약은 "무엇을 맞춰야 하는가"를, 이 기준서는 "정확히 어떤 값으로 맞추는가"를 정한다. 두 문서가 충돌하면 이 기준서가 우선하며, 이 기준서만 읽어도 실험할 수 있게 쓴다.

- 상태: **초안 r5 (팀 승인 전)**. 2026-11-09 검토 의견 7건과 대상 품목 팀 결정을 반영했다(변경 이력은 맨 아래).
- 4명이 검토한 뒤 `기준서 v1 확정` 커밋을 남기면 그 커밋 이후로 값을 바꾸지 않는다. 값을 바꿔야 하면 v2로 올리고, 영향을 받는 실험은 모두 다시 실행한다.
- `⚠ 확인` 표시는 스냅샷 담당자가 실제 KAMIS 응답으로 확인한 뒤 채우는 값이다.
- 코드 기준은 `dev` 브랜치다(검토 시점 `3de98ff`, 모델 버전 `direct-xgb-v5-huber`).

| 담당 | 모델 | 실험 ID 접두어 |
|---|---|---|
| A | XGBoost | `xgb` |
| B | LightGBM | `lgbm` |
| C | AutoARIMA | `arima` |
| D | Ridge | `ridge` |
| (공통) | naive(직전 가격 유지), mean7(최근 7일 평균) | `base` — 공통 평가기가 계산 |

## 1. 실행 환경

### 1.1 공통 의존성

- Python 3.12, 저장소 `uv.lock` 그대로. 아래 패키지를 실험 코드 기준 SHA 커밋에서 `pyproject.toml`의 `prices` 그룹에 넣고 lock을 갱신한다.

```toml
"lightgbm>=4.5,<5",
"statsforecast>=2,<3",   # AutoARIMA
"optuna>=4,<5",          # 튜닝을 쓰는 사람만. 써도 시도 횟수 상한은 동일
```

- 개인이 다른 패키지를 추가하면 안 된다. 꼭 필요하면 팀에 공유하고 lock에 반영한 새 커밋을 기준으로 4명이 다시 맞춘다.
- 실행 전 환경변수: `TZ=Asia/Seoul`, `OMP_NUM_THREADS=4`, `OPENBLAS_NUM_THREADS=4`, `MKL_NUM_THREADS=4`, `PYTHONHASHSEED=0`.
- 모델 스레드: XGBoost `n_jobs=4`, LightGBM `num_threads=4`, statsforecast `n_jobs=1`. 계열 단위 병렬 실행은 하지 않는다.
- GPU는 사용하지 않는다.

### 1.2 1·2차 비교: 로컬 실행 허용

- 실험 코드 기준 SHA에서 `uv sync --extra prices`로 만든 환경이면 로컬 실행 결과를 제출할 수 있다.
- `environment.txt`(§10.4)에 `uv pip freeze`를 남기고, 확정 lock과 다르면 결과를 받지 않는다.
- 각자 PC의 시간·메모리 값은 참고용이다. 자원 채택 판단(§8.4-6)은 §1.3 실행 값으로만 한다.

### 1.3 최종 시험: Docker, 같은 장비

| 항목 | 값 |
|---|---|
| 베이스 이미지 | `python:3.12-slim-bookworm` — 확정 시 digest(`sha256:...`) 고정 |
| 이미지 | `foodvalue-train:v1` (실험 코드 기준 SHA + `uv.lock`) |

```bash
docker run --rm \
  --cpus=4 --memory=8g --memory-swap=8g \
  -e TZ=Asia/Seoul -e OMP_NUM_THREADS=4 -e OPENBLAS_NUM_THREADS=4 -e MKL_NUM_THREADS=4 -e PYTHONHASHSEED=0 \
  -v "$PWD/data/snapshots:/data:ro" \
  -v "$PWD/experiments:/out" \
  foodvalue-train:v1 <명령>
```

- 지정 1명이 같은 장비에서 4개 모델을 순서대로 실행한다. 실행 중 다른 무거운 작업을 하지 않는다.
- 스냅샷은 읽기 전용으로 마운트하고, 결과는 `/out/<experiment_id>/`에만 쓴다.
- `.env`, API 키, DB 비밀번호는 이미지·스냅샷·결과 폴더에 넣지 않는다.

## 2. 데이터 스냅샷

### 2.1 대상 품목·계열 (팀 확정: 5개 품목)

| 품목 | 품목코드 | 소매 품종 | 도매 품종 | 등급 | 소매 단위 | 도매 단위 | 비고 |
|---|---|---|---|---|---|---|---|
| 대파 | 246 | `00` | `00` | `04` 상품 | 1 kg | 1 kg | 적재됨 |
| 양파 | 245 | `00` | `00` | `04` 상품 | 1 kg | 15 kg | 백필 필요 |
| 깐마늘 | 258 | `01` | `03`(대서) | `04` 상품 | 1 kg | 20 kg | 도매는 2019년부터 대서·남도로 나뉨. 도매 `03` 확인된 가장 이른 관측 2019-01-11(정확한 첫 관측일은 백필 후 manifest에 기록) |
| 배추 | 211 | 작형별 `06`·`01`·`02`·`03` | 작형별 `06`·`01`·`02`·`03` | `04` 상품 | 1포기 | 10 kg(그물망 3포기) | 작형 이어 붙이기 (§2.3) |
| 무 | 231 | 작형별 `06`·`01`·`02`·`03` | 작형별 `06`·`01`·`02`·`03` | `04` 상품 | 1개 | 20 kg | 작형 이어 붙이기 (§2.3) |

- 위 값은 검토 의견에서 실제 KAMIS 응답(2016~2026 중 35개 날짜)으로 확인한 것이다. 스냅샷 담당자가 manifest에 그대로 적는다.
- 깐마늘 도매처럼 소매·도매 품종이 다르면 그 사실을 manifest와 결과 보고서에 적는다.
- 배추·무는 작형별 단위가 모두 같다(위 표). 백필 결과에서 다른 단위가 나오면 이어 붙이지 않고 팀에 알린다.
- 배추·무는 공유 DB에 **작형마다 별도 품목**으로 등록되어 있다: `배추(월동)`·`배추(봄)`·`배추(고랭지)`·`배추(가을)`(`211-06/01/02/03-04`), `무(월동)`~`무(가을)`(`231-…`). 작형마다 소매·도매 계열이 있으므로 원본은 기존 스키마·`refresh_price_daily` 경로 그대로 저장된다. 스키마 변경은 필요 없다.

**계열 품질 기준 (스냅샷에 포함하는 조건)** — 배추·무는 §2.3으로 이어 붙인 뒤의 계열에 적용한다.

- 첫 관측일이 2019-11-01 이전. 검증 첫 기준일부터 5년 창을 채우기 위한 조건이며, 미달이면 2023-01-31 이전까지는 허용하되 실제 학습 시작일을 기록한다.
- 2023-01-01 ~ 2026-10-31 조사일 중 관측 비율 90% 이상
- 2023-01-01 ~ 2026-10-31 기간에 조사일 기준 7일 넘게 연속 결측이 없음 (있으면 해당 기간을 manifest에 기록하고 팀이 포함 여부 결정). 2022년 이전 결측은 품질 기준에 넣지 않고 manifest에 기록만 한다

기본은 N=10이다. 미달 계열이 있으면 팀에 알리고, 팀이 그 **품목 전체를 빼기로** 하면 남은 계열 수를 **N**으로 manifest에 기록한다. 배추·무는 작형 사이 공백 때문에 이어 붙인 뒤에도 미달할 수 있으므로, **백필 직후 가장 먼저** 확인한다(둘 다 빠지면 N=6). 비교 도중에는 계열을 빼거나 넣지 않는다. 이후 "과반"과 행 수 검사는 모두 N 기준이다.

### 2.2 스냅샷 구성

순서: (1) 품목·`price_series` 등록(배추·무는 작형별 품목, 완료) → (2) 국내 IP에서 백필 → (3) 내보내기.

```bash
uv run --extra prices python -m app.price_pipeline --start 2016-01-01 --end 2026-10-31 --collect-only
```

- 이미 수집 당일까지 받아 둔 공유 데이터는 다시 수집하지 않는다. 내보낼 때 `price_date <= 2026-10-31`(다른 표도 관측일 기준 같은 날짜)로 자르면 된다.
- 모델 학습은 최대 1,825일만 쓰지만, 수집은 2016-01부터 한다. 검증 초반 기준일의 5년 창을 채우기 위해서다.
  저장소 실험에서 2016-01부터 수집하면 5년 창 그대로도 개선됐고(8.44% → 8.86%), 학습 창을 10년으로 늘리면 나빠졌다(→ 8.01%, `xgboost/README_MODEL.md`).

배포 폴더 `data/snapshots/fv-snap-20261031-v1/`:

| 파일 | 내용 |
|---|---|
| `manifest.json` | 스냅샷 ID, 마감일, Git SHA, `flyway info` 결과, N, 파일별 SHA-256·행 수, 계열별 코드·단위·첫/마지막 관측일·관측 수·결측 구간, 생성 쿼리 |
| `price_series.csv` | 실험 계열 N개 정의. 대파·양파·깐마늘은 DB `price_series.id` 그대로. 이어 붙인 배추·무 4개 계열은 **가상 id**(9001 배추 소매, 9002 배추 도매, 9011 무 소매, 9012 무 도매)와 원본 작형 계열 id 목록(`source_series_ids`)을 함께 적는다 |
| `price_daily.csv` | 대파·양파·깐마늘 `series_id, price_date, price` (원천 결측은 행 없음. 채워 넣지 않음) |
| `price_daily_kind.csv` | 배추·무 작형별 원본 `merged_series_id, source_series_id, kind_code, price_date, price` |
| `price_daily_merged.csv` | 배추·무 이어 붙인 계열(§2.3에서 한 번 계산한 결과). 배추·무의 입력과 정답은 이 파일만 쓴다 |
| `calendar_day.csv` | 2016-01-01 ~ 2027-12-31 요일·공휴일·휴장 여부 |
| `calendar_event.csv` | 설날·추석 기간 |
| `weather_daily.csv` | 전국 ASOS 평균 (ACTUAL만. FORECAST 행 제외) |
| `exchange_rate_daily.csv` | 원/달러 |
| `item_production.csv` | 연간 생산량 `item, year, production_ton, published_from`. 품목은 실험 품목 이름(대파·양파·깐마늘·배추·무)으로 둔다 |
| `origins_validation.csv`, `origins_tune.csv`, `origins_test.csv` | 기준일 목록 (§3.3) |

- **모든 모델은 이 CSV를 읽는 공통 로더(§9)로만 입력을 받는다.** 기존 파이프라인 코드로 따로 입력을 만드는 예외는 없다. XGBoost 담당(A)도 공통 로더 인터페이스에 맞춰 구현한다.
- **DB 덤프는 실험 입력이 아니다.** 2016-01 이후 공유 DB를 가진 사람이 §9 "스냅샷 내보내기" 담당을 맡아 이 CSV 묶음과 manifest를 만들어 배포한다. DB 덤프·복원 스크립트는 그 담당자의 백업이나 탐색용으로만 쓴다.
- **생산량 품목 매핑**: 생산량 수집은 `item.name`이 KOSIS 키(`app/collectors/kosis.py`의 `PRODUCTION_SERIES`)와 정확히 같아야 연결된다(`collection_service.py`). 작형별 품목 `배추(월동)` 등과 `깐마늘`은 이름이 달라 생산량이 비게 되므로, 스냅샷 담당자가 KOSIS 키 `배추`·`무`·`마늘`로 생산량을 받아 아래처럼 연결한다. 공유 DB의 실제 품목 이름을 먼저 확인해 manifest에 적는다.

| 실험 품목 | KOSIS 키 |
|---|---|
| 대파 | `대파` |
| 양파 | `양파` |
| 깐마늘 | `마늘` |
| 배추(이어 붙인 계열) | `배추` (작형 합계 연간 생산량) |
| 무(이어 붙인 계열) | `무` (작형 합계 연간 생산량) |
- 각 CSV를 만든 SQL을 manifest의 `queries`에 남긴다. `price_daily_kind.csv` 예:

```sql
SELECT CASE WHEN i.name LIKE '배추(%' THEN '배추' ELSE '무' END AS item, s.id AS source_series_id,
       s.market, s.kind_code, d.price_date, d.price
FROM item i JOIN price_series s ON s.item_id = i.id JOIN price_daily d ON d.series_id = s.id
WHERE (i.name LIKE '배추(%' OR i.name LIKE '무(%') AND d.price_date <= DATE '2026-10-31'
ORDER BY 1, s.market, d.price_date, s.kind_code;
-- merged_series_id는 (품목, 시장)으로 9001/9002/9011/9012를 붙인다
```
- `event_item_weight`(LEARNED)와 `price_change_history`는 넣지 않는다. 마감일 시점 전체 자료로 계산된 값이라 과거 기준일에 쓰면 미래 정보가 들어간다. 필요하면 공통 로더가 기준일마다 그 시점 자료로 다시 계산한다.
- 주산지 관측소 자료는 넣지 않는다. 현재 `VERIFIED` 관측소가 없고, 두 차례 실험에서 효과가 오차 범위 안이었다(`xgboost/README_MODEL.md`).
- 원천 수정 이력은 최신 수정본만 사용한다(회고 평가 한계로 결과 보고서에 명시).
- 스냅샷 폴더는 Git에 올리지 않는다. `.gitignore`에 `data/snapshots/`, `experiments/*/model/`를 추가하고, 파일은 팀 공유 드라이브로 배포한다.

수령 후 각자 아래 출력이 manifest와 **완전히 같아야** 실험을 시작한다.

```bash
python -m tools.check_snapshot data/snapshots/fv-snap-20261031-v1   # SHA-256·행 수·계열 기간 대조 (§9)
```

### 2.3 배추·무: 작형 이어 붙이기

KAMIS는 배추(211)·무(231)를 작형별 품종 코드로만 제공한다(월동 `06`, 봄 `01`, 고랭지 `02`, 가을 `03`). 코드 하나는 연 3~5개월만 관측된다. 아래 규칙으로 소매·도매 각각 하나의 연속 계열을 만들고, **이 계열이 배추·무의 정본**이다(평가 정답도 이 계열). 모든 모델이 같은 이어 붙인 계열을 쓴다.

출하 초반에는 새 작형이 띄엄띄엄 관측되고, 겹치는 기간에는 떠나는 작형도 계속 관측된다. 그래서 **현재 작형을 유지하다가, 순환상 다음 작형이 충분히 이어질 때만 앞으로 전환**하고 되돌아가지 않는다. 소매·도매 계열마다 따로, 날짜순으로 아래를 적용한다.

**계산 시점**: 이어 붙이기는 스냅샷 담당자가 `price_daily_kind.csv`의 첫 날짜부터 마감일까지 **한 번만** 날짜순으로 계산해 `price_daily_merged.csv`로 배포한다. 로더·평가기는 이 파일에서 필요한 날짜만 잘라 쓰며, 학습 창이나 기준일에 맞춰 다시 계산하지 않는다(시작일이 다르면 결과가 달라질 수 있기 때문). 규칙이 그날까지의 관측만 쓰므로 미리 계산해도 기준일 d 시점에 d 이후 정보가 들어가지 않는다.

**순환 순서**: 월동 `06` → 봄 `01` → 고랭지 `02` → 가을 `03` → 월동 `06`. next(K)는 K의 다음 작형이다.

**월별 우선 작형** (백필 후 작형별 관측 달로 다시 확인해 manifest에 기록)

| 달 | 12~4월 | 5~6월 | 7~9월 | 10~11월 |
|---|---|---|---|---|
| 우선 작형 | 월동 `06` | 봄 `01` | 고랭지 `02` | 가을 `03` |

**규칙**

1. **시작(재시작)**: 그날 관측된 작형 중 그 달의 우선 작형을 K로 둔다. 우선 작형이 관측되지 않았으면 관측된 작형 중 순환 순서상 우선 작형 다음으로 가장 가까운 것을 고른다. 이전 작형 P는 "없음"으로 둔다.
2. **전환 후보**: K가 아니고 P(직전에 떠난 작형)도 아닌 작형 중, **next(K)** 또는 **그 달의 우선 작형**만 후보가 된다.
3. **전환**: 후보 C가 **마지막 전환일(또는 시작일) 다음 날 이후로 3 조사일 연속** 관측되면, 그 3번째 조사일부터 P = K, K = C. 같은 날 후보 둘이 조건을 채우면 그 달의 우선 작형을 고른다.
4. **그날 값**: K가 관측되면 K의 가격, 아니면 결측(앞채움 최대 7일). 전환 전 새 작형의 1~2일 관측은 쓰지 않는다.
5. **장기 공백**: K가 **10 조사일 연속** 관측되지 않았고 그 사이 전환도 없었다면, 다음으로 무언가 관측되는 날 1번으로 재시작한다(예: 2021년 이전 고랭지 미관측으로 봄 → 가을로 건너뛰는 경우).

- 방금 떠난 작형 P로는 돌아가지 않으므로, 겹치는 기간에 전환이 왕복하지 않는다. 비인접 겹침(예: 월동+고랭지)이나 세 작형 동시 관측도 2·3번으로 하나로 정해진다.
- 정상이면 계열마다 1년에 약 4회 전환한다(고랭지가 없던 해는 3회). 백필 후 소매·도매별 **연도별 전환 횟수**를 manifest에 넣고, 이 값이 크게 벗어나면 규칙을 확정하기 전에 팀에 알린다.
- `price_daily_merged.csv` 열: `series_id(9001/9002/9011/9012), price_date, price, kind_code, source_series_id, kind_switch`. `kind_switch`는 K가 바뀐 날 1.
- 고랭지 `02`는 확인한 날짜 중 2022년부터만 관측됐다(소매 2022-09-15, 도매 2022-07-14). 2021년 이전 여름에 앞채움 7일을 넘는 결측이 생기면, §5.1 규칙(v[d−28..d]에 빈 값이 있으면 특징을 만들지 않음)에 따라 그 구간은 학습 표본에서 자연히 빠진다. 백필 후 이어 붙인 계열의 연도·월별 관측 수를 manifest에 넣는다.
- 작형 전환으로 가격 수준이 크게 바뀔 수 있다. 기준일 d와 목표일 d+h의 작형이 다른 평가 점은 `kind_cross=1`로 표시해 별도로 집계한다(§8.3). 주 지표에서는 빼지 않는다.
- 이어 붙인 결과(전환일 목록, 연도별 전환 횟수)를 manifest에 남긴다. `check_snapshot`은 `price_daily_kind.csv`로 이어 붙이기를 다시 계산해 `price_daily_merged.csv`와 같은지 확인한다.
- 이어 붙이기 함수는 `tools/loader`에 하나만 둔다. 스냅샷 생성과 `check_snapshot`이 이 함수를 쓰고, 로더·평가기는 그 결과 파일을 읽는다.
- 운영 서비스가 이어 붙인 계열을 어떻게 예측·표시할지는 이 기준서 범위 밖이다. 배추·무를 운영에 넣으려면 별도로 정한다.

## 3. 예측 과제와 기준일

### 3.1 시점 규칙

- 기준일 d의 예측은 **d일 23:00 KST에 실행한다고 가정**한다.
- 자기 계열: `price_date ≤ d`인 관측 사용 가능 (KAMIS 일별 가격은 당일 오후 공표).
- 상대 시장 가격·기상·환율: `≤ d−1`. 소매·도매는 같은 KAMIS에서 공표되지만, 배치 시각에 상대 시장 값이 아직 갱신되지 않았을 수 있어 보수적으로 1일 늦춘다(저장소 `exogenous.COUNTERPART_LAG_DAYS = 1`과 동일).
- 공휴일·명절 기간·요일·연중일: 미리 확정된 정보이므로 목표일 값 사용 가능.
- 연간 생산량: Y년 값은 Y+1년 6월 30일부터 사용.
- 자기 계열의 최신 관측이 d−7일보다 오래되면 예측하지 않고 `NO_INPUT`으로 기록한다.

### 3.2 예측 대상

- 목표일 = d + h, h = 1…7 (**달력일**).
- 목표일에 실제 관측 가격이 없으면(주말·공휴일·결측) 평가 대상에서 제외한다. 예측 행은 7개 모두 제출한다.
- 학습 정답도 같다: 목표일 실제 관측이 있는 표본만, 그리고 **목표일 ≤ d인 표본만** 학습에 쓴다(D+7 표본은 7일 뒤 정답 확인 후).

### 3.3 기준일 목록

| 구분 | 기간 | 기준일 | 대략 개수 |
|---|---|---|---|
| 학습 전용 | ~ 2024-10-31 | 없음 | — |
| 검증 | 2024-11-01 ~ 2025-10-31 | KAMIS 조사일 | 계열당 약 245개 |
| 튜닝용 축소 목록 | 검증 구간 안 | 각 주의 첫 조사일 | 약 52개 |
| (간격) | 2025-11-01 ~ 2025-11-09 | 없음 — 검증 마지막 D+7 정답이 시험 구간에 걸치지 않게 함 | — |
| 최종 시험 | 2025-11-10 ~ 2026-10-23 | KAMIS 조사일 | 계열당 약 240개 |

- KAMIS 조사일 = `calendar_day.is_market_closed = false`. N개 계열에 같은 목록을 쓴다.
- 마지막 시험 기준일 2026-10-23의 D+7 = 2026-10-30이므로 모든 정답이 마감일 안에 있다.
- 튜닝용 목록은 검증 구간의 일부라, 검증 순위가 튜닝한 모델에 약간 유리하다. 4개 모델 모두 같은 조건이고 최종 시험이 따로 있으므로 허용하되 결과 보고서에 한계로 적는다.

### 3.4 재학습

- 모델 파라미터(가중치·트리·ARIMA 차수와 계수)는 **각 주의 첫 기준일에만 다시 학습**한다. 그 주의 나머지 기준일은 같은 모델에 그날까지의 최신 입력만 넣는다.
- AutoARIMA는 같은 주 안에서 새 관측으로 상태만 갱신(필터링)하는 것을 허용한다. 차수 재탐색과 계수 재추정은 주 1회.
- 재학습은 하이퍼파라미터를 다시 고르는 것이 아니다. 하이퍼파라미터는 튜닝(§6)에서 정한 값으로 고정한다.
- 최종 시험 중에도 같은 주 1회 규칙으로, 시험 기간 중 이미 관측된 가격을 포함해 재학습한다.

### 3.5 학습 단위

- 1차·2차 비교: **계열별 개별 모델**.
- D+1~D+7을 시점별 직접 모델로 할지, 시점을 특징으로 넣은 단일 모델로 할지, 재귀 예측할지는 자유. `config.json`의 `strategy`에 기록한다.
- 여러 계열을 함께 학습하는 통합 모델은 별도 실험(`*-pooled-*`)으로만 허용하고 1차 순위에는 넣지 않는다.
- 학습 대상(가격 수준·로그 가격·변화율)은 자유. 최종 출력은 원 단위 가격이다.

## 4. 결측·전처리

- 원본 결측은 데이터에서 채우지 않는다. 모델 입력을 만들 때만 **직전 관측값으로 최대 7달력일 앞채움**하고, 경과일(`price_age`)을 특징으로 제공한다.

## 5. 입력 특징

### 5.1 1차: 가격 + 공통 달력

공통 로더가 기준일 d, 시점 h별로 아래 특징을 만든다. 앞의 13개는 저장소 `PRICE_FEATURES`(`app/services/price_prediction.py`의 `features()`)와 정의가 같고, 2개(`horizon`, `days_since_kind_switch`)는 이 기준서에서 추가했다. 아래에서 v는 앞채움(최대 7일)을 적용한 달력일 가격이다.

| 특징 | 저장소 이름 | 정의 |
|---|---|---|
| `current` | `current` | v[d] |
| `lag1`, `lag7`, `lag14`, `lag28` | 같음 | v[d−k] |
| `mean7` | `mean7` | v[d−6..d]의 평균 (앞채움 값 포함) |
| `mean28` | `mean28` | v[d−27..d]의 평균 (앞채움 값 포함) |
| `change7` | `change7` | v[d] / v[d−7] − 1 |
| `volatility7` | `volatility7` | v[d−6..d] **가격 수준**의 모표준편차 (변화율이 아님) |
| `price_age` | `priceAge` | d − 최신 실제 관측일 (일) |
| `target_weekday` | `targetWeekday` | 목표일 요일 (0=월) |
| `target_season_sin`, `target_season_cos` | `targetSeasonSin`, `targetSeasonCos` | 목표일 연중일 기준 `sin/cos(2π·yday/365.25)` |
| `horizon` | (추가) | h (시점 통합 모델을 쓸 때만) |
| `days_since_kind_switch` | (추가) | 배추·무: d − 최근 작형 전환일 (최대 90으로 자름). 다른 품목은 90 |

- `days_since_kind_switch`는 기본 세트에 포함되며 쓸지 말지는 모델별로 정할 수 있다(기록 필수). AutoARIMA는 쓰지 않아도 된다.
- v[d−28..d]에 빈 값이 있으면(앞채움 7일을 넘는 결측) 그 기준일은 특징을 만들지 않는다.
- 목표일 공휴일 여부는 넣지 않는다. 공휴일에는 정답이 없어 학습·평가 표본에서 항상 0이기 때문이다. 명절 효과는 2차 EVENT 묶음에서 다룬다.
- 달력 특징(요일·연중 계절)은 미래 값을 미리 알 수 있는 정보라 **모든 모델이 똑같이 쓸 수 있다.**
  - Ridge·XGBoost·LightGBM: 위 세트를 기본으로 쓴다. Ridge는 요일 원-핫 등 모델에 맞는 변환을 해도 된다(기록 필수).
  - AutoARIMA: 같은 가격 계열을 받고, 요일 더미·`target_season_sin/cos`를 외생변수(X)로 넣을지 말지 고를 수 있다. 미래 7일 X 값은 달력으로 확정되므로 누수가 아니다. 넣는지 여부는 튜닝 시도로 비교한다.
- 이 세트 밖의 특징을 추가한 실험은 다른 `config_id`로 저장하고, **1차 순위는 기본 특징 세트 결과로 매긴다.**

**AutoARIMA 계열 구성** (둘 중 하나를 골라 기록)

- (a) 달력일 계열(앞채움 최대 7일), 계절 주기 m=7
- (b) 조사일 계열, 계절 주기 m=5. 현재 수집기는 토·일(KAMIS 미조사일)을 요청하지 않아 평일만 있다. 스냅샷 담당자가 실제 데이터에서 소매·도매 모두 주말 값이 없음을 확인해 manifest에 적은 경우에만 허용한다.
  - 매핑: 조사일 계열의 k단계 앞 = d 이후 k번째 조사일. 달력 목표일 d+h가 조사일이면 해당 단계 예측을 쓰고, 조사일이 아니면 d+h 직전 조사일의 단계 예측을 넣는다. 그 직전 조사일이 d 자신이면(예: 금요일 기준일의 토·일 목표일) v[d]를 넣는다. 이 행들은 평가에서 빠지지만 제출 행에는 값이 필요하다.
- 계절성 있음/없음은 검증 구간(튜닝 목록)에서 비교해 정한다. 결측일을 지운 계열에서 m=7을 쓰지 않는다.

### 5.2 2차: 외부변수

1차 순위가 확정된 뒤 시작한다. 분할·기준일은 1차와 같다.

| 묶음 | 변수 | 이용 시점 |
|---|---|---|
| MARKET | 상대 시장 가격, 대상/상대 비율, 상대 시장 7·28일 변화율 | ≤ d−1 |
| NATIONAL_WEATHER | 전국 평균 7일 기온·28일 강수·폭염/호우/한파 비율 | ≤ d−1 |
| EVENT | 설·추석까지/이후 일수(최대 45), 목표일 명절 영향기간 여부, 목표일 전날 공휴일 여부(**법정 공휴일만**, 대체·임시 공휴일 포함, 토·일 제외) | 목표일 값 |
| MACRO | 원/달러 7·28일 변화율 | ≤ d−1 |
| PRODUCTION | 최신 공개 연도 생산량 전년 대비 증감 | Y+1년 6/30부터 |

- MARKET의 상대 계열: 대파·양파·깐마늘은 같은 품목의 다른 시장 계열, 배추는 9001 ↔ 9002, 무는 9011 ↔ 9012. 이어 붙인 소매·도매는 전환일을 따로 정하므로 같은 날 작형이 다를 수 있다. **두 계열의 작형이 다른 날의 "대상/상대 비율"은 결측(NaN)**으로 둔다. 상대 시장 가격과 변화율은 그대로 제공하되, 작형 차이를 포함한다는 한계를 결과 보고서에 적는다.
- "목표일 공휴일 여부"는 2차에서도 쓰지 않는다. 공휴일에는 정답이 없어 표본에서 항상 0이기 때문이다(§5.1). 대신 실제 값이 나오는 "목표일 전날 공휴일 여부"를 쓴다.
- 주산지 기상(WEATHER)과 기상 예보는 사용하지 않는다. 미래 실제 기상·미래 도매가 입력은 금지.
- 외부값이 7일 넘게 비면 결측(NaN)으로 둔다. 0이나 평균으로 채우지 않는다(ASOS 빈 강수량만 0mm). 결측을 받지 못하는 Ridge는 결측 처리 방법을 학습 표본 기준으로 정해 기록한다.
- 진행: 1차에서 확정한 하이퍼파라미터를 고정한 채 "1차 + 묶음 하나"를 묶음마다 실험하고, 마지막에 "효과 있던 묶음 전체"를 실험한다.
- **AutoARIMA 2차**: 미래 7일 값이 확정되는 EVENT 묶음만 외생변수로 쓸 수 있다. 나머지 묶음은 기준일 이후 값이 필요해 해당 없음(N/A)으로 보고한다. 별도로 예측한 외생변수를 쓰려면 그 예측 과정도 백테스트에 포함해야 하며, 1차 기준서 범위에서는 하지 않는다.
- 2차 결과로 1차 순위를 소급해 바꾸지 않는다.

| AutoARIMA | `n_jobs=1`, 탐색 범위·`stepwise` 여부 명시 |

## 8. 평가

### 8.1 공통 평가 대상

- (계열, 기준일, 시점) 중 **목표일 실제 가격이 있고 naive가 계산되는 점**.
- 모든 모델이 같은 평가 대상 집합을 쓴다. 모델이 실패한 점도 대상에서 빠지지 않는다.

### 8.2 결과 종류

| 결과 | 실패 점 처리 | 용도 |
|---|---|---|
| `policy` (**주 결과**) | 실패 점을 naive 예측으로 대체 | 순위·채택 판단 ("naive 대체 정책을 포함한 운영 방식"의 성능) |
| `model_only` | 실패 점 제외, 성공률 별도 표시 | 모델 자체 성능 참고. 모델마다 표본이 다를 수 있음을 명시 |
| `common_success` | 비교하는 **모든 모델이 성공한 점만** | 성공 표본 차이를 없앤 모델 자체 비교 |

- 보고서와 선정 회의에는 세 결과와 성공률을 **모두** 낸다. "가장 좋은 모델"이라고 할 때는 `policy` 기준임을 밝힌다.
- 현재 저장소 XGBoost는 내부에서 기준 모델로 되돌아가는 선택 로직(LAST_PRICE·MEAN_7·XGBOOST_EXT 중 선택, VALIDATED 판정)이 있다. 담당 A는 **선택·복귀 로직을 끈 순수 XGBoost** 예측을 제출한다. 복귀는 `policy` 결과에서 모든 모델에 같은 방식으로만 적용한다.

### 8.3 지표와 후처리

**후처리 순서**

1. 원시 출력 `predicted_price_raw`가 NaN·무한·0 이하이면 `INVALID_VALUE`(실패)로 기록하고 예측값은 비운다.
2. 그 외에만 `predicted_price = round(predicted_price_raw)`(원 단위, 0.5는 올림)를 적용한다. 반올림 결과가 0이면 1로 둔다.

**지표**

계열 하나 안에서는 모든 평가 점의 평균, 전체는 **계열 값의 단순 평균(macro)** 을 주 값으로 한다. 점 전체 평균(micro)도 함께 보고한다.

| 지표 | 정의 |
|---|---|
| MAPE | `mean(|y − ŷ| / y) × 100` |
| MAE | `mean(|y − ŷ|)` 원 단위 (계열별로 보고) |
| rMAE | 계열별 `모델 MAE / naive MAE`. 계열마다 단위·가격대가 달라 전체 비교는 macro rMAE로 한다. naive MAE가 0인 계열은 `null`이며 macro 평균에서 빼고 그 사실을 표시한다 |
| naive 대비 상대 개선율 | `(naive macro MAPE − 모델 macro MAPE) / naive macro MAPE × 100` (계열별 값도 같은 식) |
| 계열 승률 | N개 계열 중 모델 MAPE < naive MAPE인 계열 수 |
| 성공률 | 공통 평가 대상 중 `status=OK` 비율 |
| 세부 | 계열별, 시장별, 계절별(목표일 월 기준 3–5/6–8/9–11/12–2), 시점 h별, 배추·무의 작형 전환 점(`kind_cross=1`)과 나머지 |
| 안정성 | 기준일 **월 단위 블록 부트스트랩**(1,000회, 시드 0). 통계량 Δ = `naive macro MAPE − 모델 macro MAPE`(양수면 모델이 좋음)의 95% 백분위 구간 |
| 자원 | 학습 시간 합계, 기준일당 예측 시간, 최대 RSS 메모리, 튜닝 누적 시간 |

- naive: 기준일 d의 v[d](앞채움 최대 7일)를 7개 시점에 그대로 사용. 저장소 `LAST_PRICE`와 같다.
- mean7: v[d−6..d]의 평균(앞채움 값 포함). 저장소 `MEAN_7`과 같고 §5.1 `mean7` 특징과 같은 정의다.
- naive MAPE가 0인 계열은 상대 개선율을 계산하지 않고 `null`로 표시한다.
- 겹치는 예측 구간의 오차를 독립 표본으로 보지 않는다. 그래서 유의성은 블록 부트스트랩으로만 본다.

### 8.4 채택 기준

조건은 아래 1~6이다. 어느 단계에서 무엇을 보는지는 표 아래에 정리했다.

1. macro MAPE 상대 개선율 **≥ 5%** (예: naive 5.00% → 모델 4.75% 이하)
2. macro rMAE < 1 (원 단위 오차도 naive보다 작음)
3. 계열 승률이 **과반**: `floor(N/2) + 1`개 이상 (기본 N=10이면 6개, 품목 하나가 빠져 N=8이면 5개)
4. 성공률 **≥ 99%**
5. 부트스트랩 Δ의 95% 구간 하한 **> 0**
6. 자원: 계열 1개 최종 시험 백테스트의 학습 시간 합계 **30분 이하**, 최대 메모리 **4 GB 이하**

| 단계 | 결과 | 요구 조건 |
|---|---|---|
| 검증 관문 (최종 시험 후보 선정) | 검증 구간 `policy` | 1~5 모두. 6은 각자 측정값으로 예비 확인 |
| 최종 확정 (운영 후보) | 최종 시험 `policy`, §7.3 실행 | 1·2·4·6. 3·5는 보고만 한다 |

최종 확정에서 3(계열 승률)·5(부트스트랩)를 요구하지 않는 이유: 검증 관문에서 이미 확인했고, 최종 시험은 한 번만 보는 구간이라 계열별 승패와 구간 추정의 흔들림이 크다. 이 두 조건으로 최종 시험에서 다시 떨어뜨리면 결과를 보고 기준을 바꾸고 싶은 유혹이 생긴다. 값은 반드시 보고한다.

후보 간 순위는 macro MAPE로 매긴다. 두 모델 A, B의 차이가 `|A − B| / min(A, B) < 0.02`(상대 2% 미만)이면 동률로 보고, 더 단순하고 가벼운 모델(Ridge < AutoARIMA < LightGBM < XGBoost 순으로 단순하다고 간주)을 우선한다.

- **통과하는 모델이 없을 수 있다.** 저장소 XGBoost의 대파 실험 개선율은 이 기준서와 같은 조건(2016-01부터 수집, 5년 창)에서 계절 전체 8.86%, 여름~가을 4.8%다(`xgboost/README_MODEL.md`). 이는 선택·복귀 로직을 포함하고, 가장 좋은 후보를 사후에 고른 값이라 순수 모델보다 낙관적이다. 후보가 없으면 운영은 naive를 유지하며, 이것도 정상적인 실험 결과로 보고한다.
- 1%와 1%p: MAPE 5% → 4%는 1%p 감소이자 상대 20% 개선이다. 이 기준서의 모든 "개선율"은 **상대 %**이다.
- 운영 코드의 "MAPE 상대 1% 이상 개선"보다 엄격하게 잡은 이유: 1번은 실용적으로 의미 있는 크기, 5번은 우연이 아님을 각각 확인한다. 겹치는 예측 구간 때문에 실제 독립 표본 수가 예측 건수보다 훨씬 적다.

## 9. 공통 도구 (실험 시작 전 준비)

모델 담당자와 별개로 아래 도구를 먼저 만들고, 4명이 같은 커밋을 쓴다. 단계 0 점검이 통과해야 1차 비교를 시작한다. 저장소의 `app/price_backtest.py`(기준일 재현 백테스트)와 `app/price_tuning.py`(후보 비교)를 바탕으로 만든다.

| 도구 | 역할 | 담당 | 마감 |
|---|---|---|---|
| 스냅샷 내보내기 | §2.2 CSV·manifest 생성 (배추·무 `price_daily_kind.csv`·`price_daily_merged.csv`, 가상 계열 id, 생산량 매핑 포함). 공유 DB 보유자 | ____ | ____ |
| `tools/check_snapshot` | 스냅샷 SHA-256·행 수·계열 기간을 manifest와 대조, 이어 붙이기 재계산 결과·연도별 전환 횟수 일치 확인 | ____ | ____ |
| `tools/loader` | `load_as_of(series_id, d)` — §3.1 시점 규칙대로 d 시점에 볼 수 있는 자료만 반환. §5 특징, §2.3 작형 이어 붙이기 생성 | ____ | ____ |
| `tools/run_backtest` | 기준일 목록·주 1회 재학습 일정에 따라 모델의 `fit`/`predict`를 호출하고 `predictions.csv`·시간·메모리 기록. `--phase smoke\|tune\|validation\|test` | ____ | ____ |
| `tools/evaluate` | 정답·naive·mean7을 결합해 §8 지표(`policy`·`model_only`·`common_success`, 부트스트랩) 계산, `metrics.json` 생성. 배추·무 정답은 `price_daily_merged.csv`(로더와 같은 파일)에서 읽는다 | ____ | ____ |

- 의존 순서: 스냅샷 내보내기 → `check_snapshot` → `loader`(이어 붙이기 함수 포함) → `run_backtest` → `evaluate`.
- 권장 분담: 내보내기·`check_snapshot`은 공유 DB 보유자 1명(manifest 형식을 한 번에 맞춤), `loader`·`evaluate`는 다른 1명(이어 붙이기·특징·정답 정의가 한 곳에 있음), `run_backtest`는 또 다른 1명. 담당·마감은 기준서 확정 커밋 전에 채운다.

모델 담당자는 아래 인터페이스만 구현한다.

```python
class Model:
    def fit(self, history: TrainingData, seed: int) -> None: ...
    def predict(self, inputs: OriginInputs) -> list[float | None]:  # 길이 7, h=1..7
        ...
```

- 모델 코드는 스냅샷 파일·DB를 직접 읽지 않는다(누수 방지). 정답은 평가기만 결합한다.
- 실패는 예외 또는 `None`으로 돌려주면 실행기가 상태 코드로 기록한다.
- 시간 제한: **재학습하는 기준일은 학습+예측 600초**, 예측만 하는 기준일은 60초. 넘으면 `TIMEOUT`.

## 10. 제출 형식

### 10.1 폴더와 ID

```
experiments/<experiment_id>/
```

- `config_id` = 설정 내용의 SHA-256 앞 8자리 (같은 설정이면 같은 ID)

```json
  "runtime": {"where": "local", "threads": 4},
```

### 10.3 `predictions.csv`

```csv
experiment_id,model,config_id,data_version,series_id,item_id,market,origin_date,target_date,horizon,predicted_price_raw,predicted_price,status,error_code
```

- `status`: `OK`, `NO_INPUT`(자료 부족·지연), `FIT_FAILED`, `PREDICT_FAILED`, `INVALID_VALUE`(NaN·무한·0 이하), `TIMEOUT`
- `(series_id, origin_date, horizon)` 유일, `target_date = origin_date + horizon`, 실패 행도 포함(예측값 빈칸).
- **N개 계열 × 기준일 수 × 7행**이 빠짐없이 있어야 평가기가 받는다.
- 평가기가 결합하는 열: `actual_price, naive_price, mean7_price`. 모델 제출 파일에는 넣지 않는다.

### 10.4 `environment.txt`

`git rev-parse HEAD`, 실행 위치(local/docker)와 이미지 digest, `python --version`, `uv pip freeze`, CPU 모델·코어 수, 메모리, OS.
