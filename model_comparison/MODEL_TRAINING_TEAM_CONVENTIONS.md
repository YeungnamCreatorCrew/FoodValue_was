# 4인 가격 예측 모델 학습 공통 규약

대상 모델: XGBoost, LightGBM, AutoARIMA, Ridge

목적: 4명이 Docker로 동일한 데이터를 사용하고, 동일한 조건에서 학습·평가하여 모델을 공정하게 비교한다. 이 문서는 실행 환경이나 학습 코드를 구현한 것이 아닌, 실험 시작 전에 확정할 팀 규약이다.

## 1. 가장 중요한 원칙

**같은 스키마만으로는 공정한 비교가 되지 않는다. 데이터 내용과 버전, 예측 날짜, 평가 정답, 외부정보 이용 시점까지 같아야 한다.**

- 각자 API를 호출해 만든 DB를 기준 데이터로 사용하지 않는다. 공통 스냅샷을 한 번 만들고 배포한다.
- 개인 실험 중 공통 스냅샷을 갱신하지 않는다. 수정이 필요하면 새 데이터 버전을 배포하고 관련 실험을 다시 실행한다.
- 모델별 전처리와 학습 방식은 허용하되 차이를 기록한다.
- 최종 시험 데이터로 모델 선택이나 튜닝을 하지 않는다.

## 3. Docker와 실행 환경

### 공통으로 고정할 것

- [ ] 공통 Dockerfile 또는 공통 베이스 이미지의 버전·가능하면 digest를 고정한다.
- [ ] Python 버전과 의존성 잠금 파일을 고정한다. 모델별 라이브러리 추가도 버전을 명시한다.
- [ ] PostgreSQL 메이저 버전과 확장 기능을 통일한다.
- [ ] 동일 Git 커밋의 마이그레이션을 적용하고 Flyway 이력·체크섬을 확인한다.
- [ ] DB 및 애플리케이션 시간대를 Asia/Seoul로 통일한다.
- [ ] DB 초기화·데이터 복원·학습·평가 명령을 문서화한다.
- [ ] 실험 컨테이너의 CPU·메모리 제한과 라이브러리 스레드 수를 통일한다.
- [ ] GPU 실험은 CPU 실험과 별도로 구분하고 GPU·CUDA 등 환경을 기록한다.
- [ ] 모델, 로그, 예측 결과는 컨테이너 삭제 후에도 남는 출력 경로에 저장한다.
- [ ] API 키, DB 비밀번호, 개인정보는 데이터 배포 파일과 Git에 포함하지 않는다.

현재 저장소의 `docker-compose.yml`은 개발용 PostgreSQL·Flyway·MinIO 구성이다. 이것만 실행한다고 모델 학습 환경과 자원 제한까지 통일되는 것은 아니다. 학습용 Dockerfile·서비스·실행 규칙은 별도로 준비해야 한다.

서로 다른 PC에서는 동일한 컨테이너 제한을 적용해도 실행 시간이 달라진다. 속도·메모리의 최종 비교는 같은 장비에서 순차 실행하고, DB·다른 작업의 부하 조건도 맞춘다.

## 4. 동일 데이터 스냅샷

### 배포 절차

1. 담당자 1명이 대상 데이터를 수집·정제하고 누락과 이상값을 확인한다.
2. 학습에 필요한 테이블만 포함한 DB 덤프 또는 정형 데이터 묶음을 만든다.
3. 스키마 버전, 파일 체크섬, 계열별 행 수·기간·단위가 담긴 manifest를 함께 배포한다.
4. 각자 별도 로컬 DB/볼륨에 복원한다. 기존 개인 DB와 섞지 않는다.
5. 체크섬과 복원 후 데이터 요약을 확인하고 학습을 시작한다.

### 공통 검증 항목

- [ ] 파일 SHA-256이 같고 스키마 버전이 같다.
- [ ] 테이블별 행 수와 계열별 최소·최대 날짜가 같다.
- [ ] 품목·시장·품종·등급·단위·지역 정의가 같다.
- [ ] 동일 계열·날짜의 중복 처리 및 원천 수정 버전 선택 규칙이 같다.
- [ ] 결측일, 0 이하 가격, 이상값 처리 결과가 같다.
- [ ] 원천 데이터와 정제 데이터의 대응 관계를 추적할 수 있다.

원천의 최신 수정값만 가진 스냅샷은 과거 예측 시점의 데이터와 다를 수 있다. 수정 이력이 있으면 당시 이용 가능했던 버전을 사용한다. 재현할 수 없으면 최신 수정값을 사용한 회고 평가라는 한계를 기록한다.

## 5. 예측 과제 통일

- 예측 대상은 합의된 가격 계열의 D+1~D+7 가격이다.
- 달력일 기준인지 관측일 기준인지 혼용하지 않는다. 이 규약의 기본은 달력일 기준이다.
- 각 기준일에 입력할 수 있는 최신 가격을 실행 시각과 원천 공개 시점으로 결정한다.
- 품목별로 학습할지, 여러 품목을 함께 학습할지 1차 실험에서 통일한다. 통합 학습은 별도 실험으로 분리한다.
- 가격 수준 또는 변화율 중 무엇을 학습하는지는 모델별로 선택할 수 있지만 변환·역변환을 기록하고 최종 평가는 원래 가격 단위로 한다.
- D+1~D+7을 각각 직접 예측할지, 재귀 예측할지는 모델 특성에 따라 허용하되 결과에 명시한다.
- 가격의 반올림·하한·상한 규칙을 공통 평가 코드에 둔다. 원시 출력도 보존한다.

## 6. 학습·검증·최종 시험 분할

- [ ] 날짜 무작위 분할을 사용하지 않는다.
- [ ] 학습 창과 검증·시험 기준일 목록을 공통 파일로 고정한다.
- [ ] 학습 표본은 예측 시점까지 정답이 확인된 것만 사용한다. 예를 들어 변화율 D+7 표본은 7일 뒤 정답이 확인된 후에만 학습에 넣는다.
- [ ] 겹치는 예측 구간 때문에 미래 정답이 선택·튜닝에 들어가지 않도록 분할 경계와 이용 가능 날짜를 확인한다.
- [ ] 스케일러, 결측 대체 통계, 특징 선택, 외부변수 예측기도 해당 학습 구간만으로 학습한다.
- [ ] 과거 여러 기준일에서 순차적으로 예측하는 백테스트를 사용한다.
- [ ] 모델별 재학습·재튜닝 일정과 사용 가능한 과거 자료 범위를 맞춘다.
- [ ] 최종 시험 구간에서 설정을 바꾸지 않는다.

최종 시험 중에도 정해진 운영 규칙에 따라 이미 관측된 시험 기간의 과거 가격으로 재학습하는 방식은 허용할 수 있다. 이 경우 모든 모델에 동일한 정보 이용 규칙을 적용하고, 시험 결과를 본 수동 튜닝과 구분한다.

## 7. 입력 특징과 외부변수

### 1차: 가격 기반 비교

- 공통 가격 데이터와 허용한 달력 정보만 사용한다.
- Ridge·XGBoost·LightGBM에는 공통 지연값·이동평균 등 특징 세트를 우선 제공한다.
- AutoARIMA에는 같은 원천 가격과 허용한 달력 정보를 제공하되, 내부적으로 과거값을 사용하는 방식의 차이는 허용한다.
- 특징 추가·과거 기간 변경 실험은 기본 실험과 다른 설정 ID로 저장한다.

### 2차: 외부변수 추가

- 사용 가능한 변수 목록, 단위, 집계 주기, 공개 지연, 결측 처리 규칙을 공통으로 정한다.
- 과거 기상·상대 시장 가격·환율도 예측 시점에 공개된 값만 사용한다.
- 미래 실제 기상·미래 실제 도매가를 입력하지 않는다.
- 미래 외부변수 값이 필요한 모델은 사전 확정 정보 또는 별도로 생성한 예측값을 사용한다. 외부변수 예측 과정도 백테스트에 포함한다.
- 원천 발표 시점이 없어서 공개 지연을 가정하면 그 가정을 명시한다.

AutoARIMA의 주간 계절성은 비계절 설정과 검증 구간에서 비교한다. 결측일을 제거한 뒤 7개 관측을 일주일로 해석하지 않는다.

## 8. 결측과 실패 처리

- [ ] 실제 관측 가격이 없는 목표일은 모든 모델의 공통 평가 대상에서 제외한다.
- [ ] 입력 결측을 채우는 최대 기간과 방법을 합의한다. 미래값을 이용한 보간은 하지 않는다.
- [ ] 가격 데이터가 너무 오래된 경우의 예측 불가 기준을 통일한다.
- [ ] 예측 실패·NaN·무한값·잘못된 범위는 별도 상태로 기록한다.
- [ ] 실패한 날짜를 모델별로 조용히 제외하지 않는다. 공통 평가 대상에 대한 성공률을 함께 보고한다.
- [ ] 운영용 naive 대체를 적용하면 원래 모델 결과와 대체 후 결과를 구분한다.

모델 자체의 성능과 기준선으로 대체하는 운영 정책의 성능은 별도 결과로 제출한다. 현재 XGBoost 코드의 기준선 복귀 로직을 그대로 사용한다면 다른 모델에도 동일 정책을 적용한 비교가 필요하다.

## 9. 튜닝 예산과 재현성

- 초기 비교는 기본 설정과 제한된 튜닝으로 진행한다.
- 최대 시도 횟수와 최대 실행 시간을 미리 정하고, 실제 사용량을 모두 기록한다.
- AutoARIMA 내부 차수 탐색도 탐색 비용에 포함하고 탐색 범위를 기록한다.
- 난수 시드, 조기 종료 조건, 탐색 범위, 선택 지표를 저장한다.
- 검증 성능이 비슷한 후보는 필요하면 여러 시드·여러 기간으로 안정성을 확인한다.
- 상위 1~2개 집중 튜닝은 1차 비교와 구분하고 변경된 예산을 기록한다.

## 10. 공통 평가

공통 평가 스크립트가 동일 정답과 모델별 예측 파일을 읽어 지표를 계산하도록 한다. 정답은 평가기가 결합하고, 모델 입력에는 제공하지 않는다.

| 항목 | 규칙 |
|---|---|
| MAE | 실제 가격 단위의 평균 절대 오차 |
| MAPE | 양의 실제 가격에 대한 평균 절대 비율 오차 |
| naive 대비 상대 개선율 | `(naive MAPE - 모델 MAPE) / naive MAPE × 100` |
| 성공률 | 공통 평가 대상 중 유효 예측 비율 |
| 세부 집계 | 품목·시장·계절·D+1~D+7별 |
| 자원 | 학습·예측 시간, 최대 메모리, 실제 튜닝 비용 |

- naive는 해당 예측 시점에 이용 가능한 최신 가격을 유지하는 방식으로 정의한다.
- 최근 7일 평균의 달력일·관측일 정의와 결측 처리도 고정한다.
- naive MAPE가 0이면 상대 개선율은 계산하지 않고 별도로 표시한다.
- 전체 집계에서 표본 수가 많은 계열이 결과를 지배하지 않도록 계열별 평균과 전체 예측점 평균을 구분한다. 주 선정 지표와 가중 방식은 사전에 확정한다.
- MAPE 5%→4%는 **1%p 감소이자 상대 20% 개선**이다. 상대 1% 개선과 혼동하지 않는다.
- 고정된 1%p 차이만으로 우위를 확정하지 않는다. 기간별 일관성, 표본 수, MAE, 자원을 함께 본다.
- 겹치는 날짜·예측시점의 오차를 독립 표본으로 취급하지 않는다.

## 11. 제출 파일

각 실험은 고유한 `experiment_id`를 사용하고 다음 파일을 제출한다. 파일명은 제안 규약이며 아직 구현된 인터페이스는 아니다.

| 파일 | 내용 |
|---|---|
| `config.json` | 데이터 버전, 분할, 특징, 모델 설정, 시드, 자원 제한 |
| `predictions.csv` | 공통 형식의 예측값과 성공·실패 상태 |
| `metrics.json` | 공통 평가기가 계산한 전체·세부 지표 |
| `environment.txt` | Git SHA, 이미지 digest, Python·라이브러리·장비 정보 |
| `run.log` | 학습·예측·실패 로그와 실행 시간 |

`predictions.csv` 공통 열:

```csv
experiment_id,model,config_id,data_version,series_id,item_id,market,origin_date,target_date,horizon,predicted_price_raw,predicted_price,status,error_code
```

동일 실험 내 `(series_id, origin_date, horizon)`는 유일해야 한다. `target_date`는 `origin_date + horizon`과 일치해야 한다. 실패 행도 남기고 예측값은 빈 값으로 표시한다.

평가기가 결합하는 정답·기준선 열:

```csv
actual_price,naive_price,mean7_price
```

전체 데이터나 민감 정보가 포함된 로그는 제출하지 않는다. 모델 파일은 재현·운영에 필요한 경우 별도로 보존한다.
